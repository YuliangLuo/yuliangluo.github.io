## 1. Unit 0：入门准备

官方章节：[课程介绍](https://huggingface.co/learn/agents-course/zh-CN/unit0/introduction)
·
[入门指南](https://huggingface.co/learn/agents-course/unit0/onboarding)

### 1.1 Hugging Face Hub 是什么？

Hugging Face Hub
是模型、数据集和相关项目的托管与协作平台，不是单一的模型推理服务。

-   **Model Repository：** 保存模型权重、配置、Tokenizer 和模型卡等。
-   **Dataset Repository：** 保存训练、验证或评估数据集。
-   **Space：** 托管可交互的应用演示，例如 Gradio 应用或 Agent Web UI。
-   **Inference Provider / Endpoint：**
    提供模型推理接口的服务；是否免费、支持哪些模型取决于具体提供方和套餐。

### 1.2 Hub 与 Spaces 有什么区别？

Hub 主要解决"如何共享和版本化模型、数据与代码"；Spaces
主要解决"如何把应用部署成可访问的演示"。

将 Agent 发布到 Space
并不自动意味着它具备企业级安全性。生产部署还需要身份认证、权限隔离、密钥管理、网络控制、日志、限流和运行环境隔离。

## 2. Unit 1：智能体基础

官方章节：[Introduction to
Agents](https://huggingface.co/learn/agents-course/zh-CN/unit1/introduction)

### 2.1 什么是 Agent？

**Agent（智能体）**
是一个围绕目标运行的系统：它接收任务和环境信息，利用模型进行决策，必要时调用工具，读取执行结果，并继续执行，直到达到结束条件或需要交给人处理。

一个实用的 Agent 通常包含：

1.  **模型（Model）：** 理解输入、提出下一步行动或生成回答。
2.  **指令与上下文（Instructions / Context）：**
    规定目标、约束、可用信息和行为边界。
3.  **工具（Tools）：** 让模型能够查询数据、运行计算或执行外部操作。
4.  **控制循环（Control Loop）：**
    决定何时推理、行动、观察、重试或结束。
5.  **状态与记忆（State / Memory）：**
    保存当前任务进度以及后续步骤需要的信息。
6.  **执行环境（Environment）：**
    工具运行、数据查询或实际操作发生的地方。

并非每个 Agent 都必须具备复杂的长期记忆或多个子
Agent。设计应从最小可行结构开始。

### 2.2 Agent 与普通 LLM 的区别是什么？

  对比项           普通 LLM 调用            Agent
  ---------------- ------------------------ ----------------------------------
  典型输入         一次问题或提示词         目标、上下文、工具和当前状态
  典型输出         文本或结构化结果         文本、工具调用或下一步行动
  执行流程         通常由外部程序控制       可以根据观察结果动态选择下一步
  与外部环境交互   通常由调用方完成         可通过工具交互
  复杂任务         需要应用程序拆解和串联   可在受控循环中进行任务分解与迭代

这一区别是架构层面的，而不是说 Agent 一定使用了更强的模型。Agent
可以使用与普通聊天相同的 LLM，但通过工具和控制逻辑扩展其能力。

### 2.3 什么是自主性（Autonomy）？

自主性指系统在给定目标和约束后，能够自行选择部分后续步骤，而不必让人指定每一个动作。

自主性不是越高越好。高自主性通常意味着更多灵活性，也意味着更难预测的执行路径、更高成本和更大的权限风险。对于删除文件、发送邮件、修改生产参数等高影响操作，应设置确认点和权限边界。

### 2.4 LLM 在 Agent 中扮演什么角色？

LLM 是 Agent 的决策与语言理解组件，但不等于整个 Agent 系统。

LLM 通常负责： - 解释自然语言任务； - 根据上下文判断下一步需要什么； -
选择工具并生成参数； - 将工具结果整合为后续决策或最终回答。

应用程序仍然需要负责工具执行、权限检查、状态管理、超时、重试、异常处理和最终结果验证。**模型提出行动，不代表行动已经成功执行。**

### 2.5 什么是 Token、Message 和 Chat Template？

**Token：**
模型处理文本或多模态内容时使用的基本编码单元，不等同于一个完整单词。上下文窗口和推理成本通常与
Token 数量有关。

**Message：**
对话通常由多条消息组成，每条消息带有角色和内容。常见角色包括： -
`system`：系统级行为约束； - `developer`：应用开发者设定的指令； -
`user`：用户输入； - `assistant`：模型输出； -
`tool`：工具执行后返回的结果。

不同 API
对角色和消息结构的支持可能不同，应以所使用模型或接口的规范为准。

**Special Tokens：**
用于标识消息边界、角色、控制流或多模态结构的特殊标记，不是普通自然语言单词。

**Chat Template：**
将结构化消息转换成模型训练或推理时预期的序列格式。不同模型可能使用不同模板。模板不匹配可能导致模型误判角色、不能正确发起工具调用或输出异常格式。

**关键理解：**
工具调用既是内容格式问题，也是控制流问题。模型必须生成可被运行时正确识别的调用，运行时执行工具后再把结果交回模型。

### 2.6 什么是 Tool？

Tool（工具）是 Agent
可调用的外部能力接口，例如数学计算、数据库查询、文件检索、网络搜索、受限代码执行、业务
API 或测试任务触发。

一个清晰的工具定义通常需要： - **名称：** 准确表达用途； - **描述：**
说明适用场景和限制； - **参数 Schema：**
定义参数名、类型、必填项和约束； - **执行函数：** 真正完成操作； -
**返回结果：** 结构化、可解释且便于模型继续处理； - **错误处理：**
将失败原因转换为可诊断的结果； - **权限边界：**
限定工具能访问和修改的资源。

工具设计应遵循"接口越清晰，模型越容易正确使用"的原则。避免一个工具同时承担过多无关功能，也不要让模型直接获得超出任务需要的权限。

### 2.7 什么是 Thought--Action--Observation 循环？

这是理解 Agent 执行过程的核心抽象：

1.  **Thought（思考）：** 根据目标、指令和当前状态判断下一步。
2.  **Action（行动）：** 选择工具并提交参数，或者执行其他允许的动作。
3.  **Observation（观察）：** 接收工具结果、错误或环境状态变化。
4.  **循环：** 根据观察结果继续下一步，或者判断任务已完成。

``` text
用户目标
   ↓
模型判断下一步
   ↓
选择工具并生成参数
   ↓
运行时检查权限并执行工具
   ↓
返回结果或错误
   ↓
模型结合新结果继续决策
   ↓
任务完成 / 继续循环 / 转交人工
```

这不是保证 Agent
一定正确的算法。错误工具选择、错误参数、工具异常、过早结束和无限循环都可能发生，因此必须有终止条件、超时和最大步数限制。

### 2.8 什么是 ReAct？

ReAct 是 Reasoning + Acting
的思路，即把推理与行动结合起来：模型不只是生成最终答案，还可以在执行过程中选择动作、观察结果，再调整后续步骤。

它的价值在于让行动依赖实际反馈，而不是要求模型一次性猜出完整答案。它也有成本：多轮模型调用会增加延迟和
Token 消耗，错误决策可能逐步累积。

ReAct 是一种 Agent
设计模式，不是某个特定框架，也不意味着应该公开模型所有内部推理内容。工程系统应记录可审计的决策摘要、工具调用和执行结果。

### 2.9 Action 与 Observation 分别是什么？

-   **Action** 是 Agent
    提出的操作，例如搜索关键字、调用计算函数或读取文件。
-   **Observation** 是执行后的事实反馈，例如搜索结果、计算值、API
    状态码或异常消息。

Action 是意图；Observation
是执行后的证据。两者不能混为一谈。例如，模型请求运行测试不等于测试已经通过，只有测试执行器返回的结果才能作为判断依据。

### 2.10 为什么课程要介绍 Dummy Agent Library？

简化的 Agent 实现让学习者看清楚框架背后的机制，而不是一开始就被复杂 API
遮蔽。重点是理解 Agent
循环、工具调用、结果返回和结束条件，并识别框架替开发者封装了哪些重复逻辑。

### 2.11 第一个 smolagents Agent 要理解什么？

课程用简单任务构建
Agent，并介绍如何分享应用。学习重点不只是让演示成功，而是明确区分： -
模型推理； - 工具定义； - 工具执行； - Agent 控制循环； - 最终答案； -
部署和共享。

## 3. Unit 2.1：smolagents

官方章节：[smolagents
模块](https://huggingface.co/learn/agents-course/zh-CN/unit2/smolagents/introduction)

### 3.1 smolagents 解决什么问题？

`smolagents` 是一个轻量级 Agent
框架，帮助开发者组织模型、工具和执行循环。它适合用来理解 Agent
机制并快速构建小型智能体。

使用框架的价值是减少样板代码；代价是需要理解框架的执行约定、模型接口和安全边界。框架不会自动保证任务正确，也不会自动消除工具执行风险。

### 3.2 CodeAgent 与 ToolCallingAgent 有什么区别？

  -------------------------------------------------------------------------------------------------------
  维度                    CodeAgent                            ToolCallingAgent
  ----------------------- ------------------------------------ ------------------------------------------
  模型主要生成什么        可执行代码                           结构化工具调用，通常是 JSON 风格参数

  执行方式                在受控执行环境运行代码               运行时解析调用并执行对应工具

  优势                    可组合多个步骤，表达灵活             接口明确，工具调用边界相对清楚

  主要风险                代码执行带来的权限、资源和安全风险   参数错误、工具选择错误、接口表达能力限制

  适用情况                需要灵活组合计算或程序步骤           工具集合清晰、希望控制每次操作范围
  -------------------------------------------------------------------------------------------------------

这不是"代码 Agent
一定更强"的比较。选择取决于模型的代码能力、任务结构、可用工具、执行环境的隔离能力和安全要求。

### 3.3 什么是 Tool Calling Agent？

Tool Calling Agent
不直接让模型任意执行操作，而是让模型从定义好的工具中选择，并生成符合接口约定的参数。运行时负责校验、执行和返回结果。

关键环节： 1. 把工具说明和参数 Schema 提供给模型； 2.
模型选择工具并产生参数； 3. 运行时验证参数与权限； 4.
执行工具并捕获异常； 5. 将结果作为 Observation 交回 Agent。

即使调用格式合法，也不代表调用在语义上正确；仍需校验结果和业务规则。

### 3.4 工具应如何设计？

-   采用明确的名称、描述和输入输出 Schema。
-   对参数做类型、范围、格式和权限验证。
-   尽量让工具执行单一、可测试的操作。
-   返回结果应包含足够上下文，但避免返回无关的大量数据。
-   对超时、限流、网络错误和业务失败提供可识别的错误结果。
-   对写操作设置幂等键、审计日志或人工确认机制。

### 3.5 什么是 Retrieval Agent？

Retrieval Agent
可以把检索能力作为工具，按需查询文档或知识库，再将检索结果用于回答。

与固定 RAG 流程相比，Agent
可以在检索之外选择其他工具，或者根据第一次检索的结果决定是否进一步搜索。但这种灵活性也会增加执行路径和评估复杂度。

### 3.6 什么是 Multi-Agent System？

多 Agent 系统由多个具有不同职责或上下文的 Agent
协同完成任务。常见分工包括： - Planner：拆解目标、制定计划； -
Researcher：查找资料； - Executor：执行具体操作； -
Reviewer：检查结果或提出修改； - Coordinator：分派任务并汇总结果。

多 Agent 并不必然优于单
Agent。它会引入通信成本、状态同步、重复工作、责任归属和错误传播等问题。若一个
Agent 配合几个确定性工具就能完成任务，通常不必急于拆成多个 Agent。

### 3.7 视觉 Agent 与浏览器 Agent 有什么特别之处？

视觉 Agent 处理图像或视觉模型输出；浏览器 Agent
通过网页内容或浏览器交互获取信息、完成操作。

两类 Agent 都面临额外风险： - 页面内容可能包含提示注入； -
页面布局和内容可能变化； - 截图或 DOM 信息可能不完整； -
浏览器会话可能包含敏感数据； -
点击、提交、删除等动作可能造成真实副作用。

应将网页视为不可信输入，并对重要动作做确认、权限控制和执行后验证。

## 4. Unit 2.2：LlamaIndex

官方章节：[LlamaIndex
模块](https://huggingface.co/learn/agents-course/zh-CN/unit2/llama-index/introduction)

### 4.1 LlamaIndex 主要解决什么问题？

LlamaIndex 强调把 LLM
应用连接到外部数据、索引、检索组件和工作流。它尤其适合需要围绕企业文档或业务数据构建检索与问答能力的应用。

课程重点包括组件、工具、Agent 和工作流。

### 4.2 什么是 LlamaHub？

LlamaHub
提供数据连接器和集成工具，帮助应用从文件、数据库、服务或其他来源加载数据。连接器解决的是"如何接入数据"，并不自动保证数据质量、权限正确或检索结果准确。

企业环境仍需考虑数据访问控制、同步周期、删除传播、来源追踪和数据版本。

### 4.3 什么是 RAG Pipeline？

RAG（Retrieval-Augmented
Generation，检索增强生成）在生成回答前检索外部资料，并把相关内容提供给模型。典型流程包含：

1.  **Loading：** 从文件、网站、数据库或 API 读取数据；
2.  **Indexing：** 将数据转换为可查询的结构，例如切分文本并计算
    Embedding；
3.  **Storing：** 保存向量、文本、元数据和索引；
4.  **Retrieval / Querying：** 根据查询找到相关内容；
5.  **Generation：** 将检索内容作为上下文交给模型；
6.  **Evaluation：** 评估检索相关性、回答正确性、忠实性和延迟。

Embedding
是文本或其他内容的向量表示。向量相似度有助于寻找语义相关内容，但不保证检索结果一定正确；关键词检索、元数据过滤和混合检索也可能是必要的。

### 4.4 什么是 QueryEngine？

`QueryEngine`
把查询逻辑封装成可调用的接口，可以承担检索和回答任务。它可以进一步包装成
Agent 工具，让 Agent 在需要查询知识库时调用。

需要区分： - **Retriever：** 找出相关数据片段； - **Query Engine：**
将检索与查询处理组织成更高层的问答接口； - **Agent：**
决定何时调用该接口、是否需要其他工具以及如何整合结果。

### 4.5 LlamaIndex 的工具类型有哪些？

课程涉及的主要工具形式包括：

-   **FunctionTool：** 将 Python 函数包装为工具；
-   **QueryEngineTool：** 将查询引擎包装为工具；
-   **ToolSpec：** 将一组相关工具组织成可复用的工具集合；
-   **Utility Tools：** 帮助处理工具返回的大量数据或执行辅助操作。

工具的描述和输入输出定义会影响 Agent 是否能正确选择和使用它们。

### 4.6 什么是 LlamaIndex Agent？

Agent
可以根据用户目标选择工具、读取结果并继续决策。工具可以是普通函数，也可以是检索引擎或其他封装后的能力。

关键问题不是"Agent 是否调用了工具"，而是： - 工具选择是否合理； -
参数是否正确； - 返回结果是否支持结论； - 是否需要继续检索； -
何时应该停止并给出答案。

### 4.7 什么是 LlamaIndex Workflow？

Workflow
是将任务组织为一组可管理步骤的方式。课程强调由事件触发步骤，步骤再发出事件以推进后续流程。

与完全依赖模型自由决策的循环相比，显式 Workflow
更容易控制顺序、分支、并发和异常处理。并非所有工作流都需要
Agent；固定、可预测的业务步骤往往适合使用确定性流程，只有需要动态选择时才引入模型决策。

## 5. Unit 2.3：LangGraph

官方章节：[LangGraph
模块](https://huggingface.co/learn/agents-course/zh-CN/unit2/langgraph/introduction)

### 5.1 LangGraph 解决什么问题？

LangGraph 通过图结构组织复杂 LLM
应用。它适合需要显式控制状态、循环、条件分支、持久化或人工介入的工作流。

它关注的不只是"如何调用模型"，还包括"流程如何前进、状态如何更新、失败后如何恢复"。

### 5.2 什么是 State、Node 和 Edge？

-   **State（状态）：**
    当前任务的共享数据，例如输入、分析结果、待执行动作、工具结果和错误信息。
-   **Node（节点）：** 执行一个步骤的逻辑，例如调用
    LLM、运行工具、验证结果或请求人工确认。
-   **Edge（边）：** 指定一个节点执行后流程如何转移。
-   **Conditional Edge（条件边）：**
    根据状态或判断结果选择不同的后续节点。
-   **Loop（循环）：**
    让流程在满足条件时返回先前节点，例如反复检查和修正结果。

图结构使流程可视化，并把"模型生成什么"与"程序允许走哪条路径"分开。

### 5.3 为什么有状态工作流很重要？

复杂任务可能跨越多次模型调用、工具调用甚至人工审核。状态可记录已经完成的步骤，避免每次从头开始，也有利于恢复和审计。

但状态设计不当会造成数据膨胀、字段冲突或旧信息被错误复用。状态字段应有清晰定义，敏感信息应受到保护，状态迁移应能被测试。

### 5.4 LangGraph 与普通链式调用有什么区别？

简单链式调用通常按照固定顺序执行；图式工作流可以包含分支、循环、多个路径和显式状态更新。

当任务有复杂条件、需要重试、人工审核、长期运行或恢复执行时，图结构通常更合适。对于简单的"输入---模型---输出"，使用
LangGraph 可能增加不必要的复杂度。

### 5.5 课程案例：邮件分拣与文档分析

这类案例用于展示如何把现实任务拆成节点，例如： 1. 读取输入； 2.
分类或提取信息； 3. 判断是否需要进一步分析； 4. 调用工具或生成结果； 5.
校验结果； 6. 必要时转交人工。

真正重要的是状态和控制流设计，而不是单纯复现案例中的某个 API。

### 5.6 smolagents、LlamaIndex 与 LangGraph 如何选择？

  -----------------------------------------------------------------------------------------------------------
  需求                                       优先考虑                原因
  ------------------------------------------ ----------------------- ----------------------------------------
  快速理解 Agent 循环、工具调用和代码 Agent  smolagents              结构轻量，适合直接探索 Agent 行为

  文档检索、企业数据接入、RAG 组件           LlamaIndex              数据加载、索引、检索和工具集成是其强项

  显式状态、复杂分支、循环、恢复和人工审核   LangGraph               便于管理流程与状态转换

  简单、固定的业务步骤                       普通 Python 工作流      更容易测试、调试和控制成本

  需要多个能力                               组合使用，但明确职责    避免多个框架重复管理同一状态或控制流
  -----------------------------------------------------------------------------------------------------------

框架不是互斥的技术路线。选型应依据业务流程、团队经验、部署约束、可观测性和维护成本，而不是只比较功能清单。

## 6. Unit 3：Agentic RAG

官方章节：[Agentic RAG
用例](https://huggingface.co/learn/agents-course/unit3/agentic-rag/agentic-rag)

### 6.1 什么是 Agentic RAG？

Agentic RAG 将检索能力作为 Agent 可以选择使用的工具。Agent
不必每次都按固定的"检索一次---生成回答"流程执行，而是可以根据任务决定是否检索、使用哪一个检索工具、是否补充搜索，以及何时停止。

例如，为活动策划提供支持的 Agent 可能需要： - 查询内部宾客资料； -
搜索最新新闻； - 查询天气； - 获取外部平台统计； -
汇总结果并检查信息是否足够。

### 6.2 标准 RAG 与 Agentic RAG 有什么区别？

  ---------------------------------------------------------------------------------------------
  维度                    标准 RAG                       Agentic RAG
  ----------------------- ------------------------------ --------------------------------------
  流程                    通常按预设步骤检索再生成       可由 Agent 动态选择检索和其他工具

  决策位置                主要由应用代码或固定流程决定   部分决策交由模型根据任务和结果决定

  多工具组合              需要预先设计流程               可以动态路由到不同工具

  可预测性                通常较高                       执行路径可能变化

  成本与延迟              较容易估算                     可能因多轮决策和多次调用而增加

  评估难点                检索质量和回答质量             还要评估工具选择、步骤规划和终止决策
  ---------------------------------------------------------------------------------------------

Agentic RAG 不是所有 RAG 的默认升级。简单的知识问答通常可从标准 RAG
开始；当任务需要动态路由、迭代检索或结合多种数据源时，Agentic RAG
才更有价值。

### 6.3 为什么要把 RAG 封装成 Tool？

封装为 Tool 可以把数据检索的复杂细节隐藏在稳定接口后面，让 Agent
只需要知道： - 什么时候适合查询； - 需要提供哪些参数； -
结果会以什么格式返回； - 结果有哪些限制。

这有助于分离职责：检索模块负责找资料，Agent
负责决定何时使用检索结果以及如何组合其他能力。

### 6.4 Agentic RAG 的典型失败模式

-   查询表达不准确，导致检索不到关键资料；
-   召回内容相关但不能支持结论；
-   Agent 过度检索，造成延迟和成本上升；
-   不同来源信息冲突，Agent 没有识别冲突；
-   把检索内容中的恶意指令当成可信指令；
-   缺少引用或来源记录，无法核验回答；
-   没有终止条件，反复搜索同一内容。

缓解方法包括查询改写、混合检索、元数据过滤、来源引用、结果验证、最大步数限制、可信度规则和人工升级机制。

### 6.5 课程用例的概念重点

课程以活动策划为例，组合宾客资料检索、网络搜索、天气查询和其他工具。其核心不是活动策划本身，而是展示一个
Agent 如何在多个工具之间进行选择、整合结果，并根据新信息调整后续步骤。

## 7. Unit 4：最终项目与 GAIA

官方章节：[最终项目介绍](https://huggingface.co/learn/agents-course/en/unit4/introduction)

### 7.1 什么是 GAIA？

GAIA 是用于评估通用 AI
助手能力的基准之一，任务可能需要推理、工具使用、信息检索和多步骤操作。课程要求构建
Agent，并在指定的 GAIA 子集上评估表现。

基准测试的意义是用相对统一的任务和评分方法比较系统，而不是只凭演示效果判断
Agent 是否有效。

### 7.2 为什么 Agent 需要基准测试？

Agent
的回答可能看起来合理，但任务实际没有完成。评估应把"看起来不错"转化为可比较的指标。

常见维度： - **任务成功率：** 最终结果是否满足要求； - **答案正确性：**
答案是否正确； - **工具使用质量：** 是否选择合适工具并正确传参； -
**过程效率：** 工具调用次数、模型调用次数和总延迟； - **成本：**
Token、模型推理和外部服务开销； - **稳健性：**
面对边界输入、工具失败和信息冲突时是否仍能工作； - **安全性：**
是否越权、泄露数据或执行不允许的操作。

### 7.3 如何理解评估分数？

分数只对特定数据集、评分规则和测试环境有效。不同基准之间不能直接比较。测试集上的提升也不一定代表真实生产环境一定改善。

有效的评估流程应包括固定数据集、记录模型和提示词版本、保存工具轨迹、重复测试、分析失败案例，并在修改后重新运行回归测试。

## 8. 附加单元 1：函数调用微调

官方章节：[为函数调用微调
LLM](https://huggingface.co/learn/agents-course/zh-CN/bonus-unit1/introduction)

### 8.1 什么是 Function Calling？

Function
Calling（函数调用）是模型按预定格式提出工具调用请求的机制。模型通常不会直接执行函数；实际执行由运行时完成。

典型过程： 1. 将工具名称、描述和参数 Schema 提供给模型； 2.
模型生成工具调用请求； 3. 运行时校验调用并执行工具； 4.
将工具结果返回给模型； 5. 模型继续决策或生成最终答案。

Function Calling
是模型与外部程序之间的接口协议，不等于模型获得了任意执行代码的能力。

### 8.2 Prompt Engineering、RAG 与 Fine-tuning 有什么区别？

-   **Prompt Engineering：**
    通过指令、示例和上下文引导现有模型行为，不修改模型权重。
-   **RAG：** 在推理时检索外部知识，不必通过训练把所有知识写进模型权重。
-   **Fine-tuning：**
    使用训练数据更新模型参数，让模型在特定任务上形成更稳定的行为模式。
-   **Tool / Runtime Engineering：**
    改善工具接口、权限、执行和错误处理，不依赖改变模型参数。

这些方法解决的问题不同，通常可以组合使用。

### 8.3 为什么要微调函数调用能力？

当模型反复出现格式错误、参数遗漏、工具选择不稳定或特定工具调用模式不可靠时，可以评估微调是否值得投入。

但微调不能代替运行时验证。即使模型学会生成正确格式，工具仍可能失败，参数仍可能违反业务规则，模型也可能在训练分布之外犯错。

### 8.4 什么是 SFT 与 LoRA？

**SFT（Supervised Fine-Tuning，监督微调）：**
使用输入与目标输出配对的数据训练模型，让模型学习期望行为。

**LoRA（Low-Rank Adaptation）：**
一种参数高效微调方法，通过训练额外的低秩适配参数来调整模型行为，通常比更新全部权重需要更少的训练资源。

函数调用训练数据应覆盖正常工具选择、正确参数格式、多步调用、工具结果处理、不应调用工具的情况、工具失败后的恢复，以及无权限请求。

评估不能只看输出 JSON
是否合法，还应验证工具选择、参数语义、任务成功率和安全边界。

## 9. 附加单元 2：可观测性与评估

官方章节：[Agent
可观测性与评估](https://huggingface.co/learn/agents-course/zh-CN/bonus_unit2/introduction)

### 9.1 什么是 Observability？

可观测性是通过日志、指标和追踪等外部信号，理解系统内部正在发生什么的能力。Agent
的执行路径会因输入和模型决策而变化，因此只记录最终答案通常不够。

### 9.2 Logs、Metrics 与 Traces 有什么区别？

  --------------------------------------------------------------------------
  类型                    主要回答的问题             示例
  ----------------------- -------------------------- -----------------------
  Logs（日志）            某个事件具体发生了什么？   工具参数校验失败、API
                                                     返回错误

  Metrics（指标）         系统总体表现如何？         成功率、P95 延迟、Token
                                                     用量、错误率

  Traces（追踪）          一次任务经过了哪些步骤？   用户请求 → LLM →
                                                     检索工具 → LLM →
                                                     最终回答
  --------------------------------------------------------------------------

对于 Agent，Trace
尤其重要，因为它可以把多个模型调用和工具调用串成一条任务执行链。

### 9.3 OpenTelemetry 与 Langfuse 等工具有什么作用？

OpenTelemetry 提供通用的遥测数据采集与传递规范。Langfuse、Arize
等平台可以帮助收集、查看和分析 LLM
应用的追踪与评估数据。具体工具的功能和集成方式会随版本变化。

需要关注的指标包括任务成功率、模型和工具调用次数、输入与输出
Token、估算成本、总延迟与分步骤延迟、工具错误率、重试率、用户反馈以及安全事件。

### 9.4 在线评估与离线评估有什么区别？

**在线评估：**
在真实使用过程中收集反馈、追踪质量和成本，发现实际流量中的问题。需要注意隐私、数据保留和反馈偏差。

**离线评估：**
使用固定数据集或基准任务反复测试。适合比较模型、提示词、工具定义和流程版本，便于回归测试。

课程涉及使用 LLM 作为评判者（LLM-as-a-Judge）以及使用基准数据集（例如
GSM8K）进行评估。LLM
评判者本身也可能有偏差，因此重要结论应配合规则评分、人工抽查或可靠的标准答案验证。

### 9.5 如何调试失败的 Agent 任务？

1.  用户目标是否被正确理解？
2.  模型是否选择了合适的下一步？
3.  工具名称和参数是否正确？
4.  运行时是否通过权限与 Schema 校验？
5.  工具是否真正成功执行？
6.  返回结果是否完整、可信且可用？
7.  Agent 是否正确解释结果并判断是否结束？
8.  最终答案是否满足任务验收条件？

如果没有执行轨迹，就很难区分失败来自模型、工具、数据、权限还是流程控制。

## 10. 附加单元 3：游戏中的 Agent

官方章节：[从 LLM 到 AI
Agent：Pokémon](https://huggingface.co/learn/agents-course/zh-CN/bonus-unit3/from-llm-to-agents)

### 10.1 为什么用游戏研究 Agent？

游戏提供一个状态明确、行动受约束、结果可观察的环境。Agent
必须读取当前状态、选择合法动作、观察动作后果，再调整策略，因此适合展示
Agent 的完整循环。

### 10.2 普通 LLM 对话与游戏 Agent 有什么区别？

普通 LLM 可以生成自然语言建议；游戏 Agent
则需要将建议转化为环境可执行的动作，并根据游戏状态持续决策。

``` text
读取游戏状态
    ↓
选择策略或行动
    ↓
验证动作是否合法
    ↓
执行动作
    ↓
读取新的游戏状态
    ↓
继续决策，直到达到结束条件
```

### 10.3 游戏 Agent 可以学到哪些通用概念？

-   **State：** 当前环境状态；
-   **Action Space：** 允许采取的动作集合；
-   **Planning：** 对后续行动进行规划；
-   **Feedback：** 根据动作结果调整策略；
-   **Memory：** 利用过去的行动和结果；
-   **Evaluation：** 用胜率、任务完成率、资源消耗等指标评价表现。

这些概念也适用于软件测试、浏览器自动化和机器人控制等任务。关键差异在于环境的状态、动作空间和风险等级。

## 11. 跨章节核心问题

### 11.1 Agent 与 Workflow 有什么区别？

Workflow 是步骤和控制流的组织方式；Agent
是能够根据目标和上下文进行一定程度动态决策的系统。两者可以组合：Workflow
负责确定性流程，Agent 负责需要判断的局部步骤。

**工程原则：** 能用确定性代码稳定完成的步骤，不必全部交给 LLM。

### 11.2 单 Agent 与多 Agent 如何选择？

优先从单 Agent
加工具开始。只有在任务确实需要不同上下文、独立职责、并行执行或独立验证时，再考虑拆分为多个
Agent。

拆分前应确认收益能否抵消更多模型调用和通信成本、状态同步复杂度、重复执行和冲突、更难定位的失败，以及权限与审计面的扩大。

### 11.3 Tool Calling 与 Code Execution 有什么区别？

Tool Calling 让模型从预定义接口中选择操作；Code Execution
允许模型生成程序并在执行环境中运行。前者通常更容易限制可用动作，后者表达能力更灵活，但执行隔离和资源限制要求更高。

两者都需要输入验证、权限控制、超时、审计和结果校验。

### 11.4 RAG、微调与提示词工程如何选择？

  需求                                 优先考虑
  ------------------------------------ ----------------------------
  需要访问最新或私有文档               RAG / 数据工具
  模型不理解任务格式或调用模式不稳定   提示词优化；必要时评估微调
  需要改变特定任务的输出行为           SFT / LoRA 等微调方法
  需要访问实时系统或执行操作           Tool Calling / API
  需要可恢复的复杂流程                 Workflow / 状态图
  需要判断哪种方法有效                 固定评估集与回归测试

这些方案并不互斥。企业系统通常由模型、检索、工具、流程控制和评估组成，而不是只靠一个模型解决所有问题。

### 11.5 为什么 Agent 必须有终止条件？

Agent
循环可能反复调用工具、重复检索或不断修正答案。没有终止条件会造成成本失控和任务卡死。

常见限制： - 最大步骤数； - 总时间预算； - 最大模型调用次数； -
最大工具调用次数； - 重试上限； - 结果质量阈值； - 人工确认或升级条件。

### 11.6 Agent 的安全边界应该放在哪里？

不要只依靠提示词要求模型"不要做危险操作"。应在工具运行时实施权限控制。

建议： - 工具只开放完成任务所需的最小权限； -
将只读工具与写入工具分开； -
对外部输入、检索文档和网页内容按不可信数据处理； -
对重要写操作设置人工确认； -
隔离代码执行环境并限制网络、文件系统和资源； -
对密钥、个人信息和企业数据实施访问控制； -
记录可审计的工具调用与结果； - 对失败、超时和异常提供安全的默认行为。

### 11.7 怎样判断 Agent 是否真的完成任务？

不要只检查模型是否生成"完成"之类的文本。应依据可验证的外部证据判断，例如测试执行器的真实结果、数据库事务的提交状态、文件是否存在且内容符合要求、API
返回状态和业务结果，以及输出是否满足预定义验收条件。

**完成声明应建立在执行证据之上。**

## 12. 核心术语表

  ------------------------------------------------------------------------------------------------
  术语                                含义
  ----------------------------------- ------------------------------------------------------------
  Agent                               根据目标和上下文进行决策、调用工具并根据结果继续执行的系统

  LLM                                 大语言模型，负责语言理解、生成和部分决策

  Tool                                Agent 可调用的外部能力接口

  Function Calling                    模型以约定格式提出函数或工具调用请求的机制

  ReAct                               将推理与行动结合，并根据观察结果继续决策的设计思路

  Observation                         工具或环境执行后返回的事实反馈

  State                               任务当前的结构化状态

  Memory                              为后续决策保存和检索的信息；可以是会话内或长期记忆

  Workflow                            将任务组织为步骤、分支和控制流的方式

  Node / Edge                         图工作流中的执行单元与流程连接

  RAG                                 生成前检索外部资料并将其作为上下文提供给模型

  Agentic RAG                         由 Agent 动态决定何时、如何检索以及是否调用其他工具的 RAG
                                      架构

  Embedding                           将文本或其他内容映射为向量表示的方法

  Index                               为高效查询而构建的数据结构

  Schema                              对数据字段、类型和约束的结构化定义

  SFT                                 使用示例输入和目标输出进行监督微调

  LoRA                                通过低秩适配参数进行参数高效微调的方法

  Observability                       通过日志、指标和追踪理解系统运行状态的能力

  Trace                               一次请求经过的多个步骤和调用组成的执行轨迹

  Benchmark                           用于比较系统表现的固定任务集合与评分规则

  GAIA                                用于评估通用 AI 助手能力的基准之一

  LLM-as-a-Judge                      使用 LLM 对输出或执行结果进行评分的评估方法

## 13. 建议的学习顺序

1.  **先掌握 Unit 1：** 能够解释 Agent、Tool、Message、Chat
    Template、ReAct 和 Thought--Action--Observation 循环。
2.  **再学 smolagents：** 构建一个能调用工具并处理错误的简单 Agent。
3.  **学习 LlamaIndex：** 理解数据加载、索引、检索、QueryEngine、工具与
    Workflow 的关系。
4.  **学习 LangGraph：** 用 State、Node、Edge
    和条件分支构建可控的多步骤流程。
5.  **完成 Agentic RAG：**
    将知识检索与至少一个外部工具组合，测试何时需要继续检索。
6.  **学习可观测性：** 为每次任务保存
    Trace、成本、延迟、工具结果和最终验收结果。
7.  **完成 GAIA 或自建任务集：**
    形成可重复运行的评估集，基于失败案例迭代。
8.  **最后学习函数调用微调：**
    当提示词、工具接口和运行时已合理，但模型行为仍不稳定时，再评估微调的收益。
